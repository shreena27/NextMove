### Recorded deviations from the prototype (each is deliberate; each ships with a test)

- **D1 — the `.demo-hint` "any 6 digits work here" line is NOT ported.** `renderSaveOtp` (**3862**) renders `<div class="demo-hint">Design prototype: any 6 digits work here.</div>`. With a real OTP it is false, and it announces to a citizen that their code does not matter. This is a **subtraction**, on exactly the principle C5's OQ1(b) and C6's D8 already established: *"never invent copy" forbids authoring, not omitting a sentence that is untrue in this chunk*. The `.demo-hint` CSS class is still lifted (it sits inside the contiguous 662-743 range and carving it out would fork the transcription) but is **unused**, and is labelled as such in `index.css`'s provenance header — the same treatment C5 gave `.saved-actions`/`.saved-continue`/`.saved-remove`. Task 12 carries a test asserting the string does not render.
- **D2 — the OTP resend cooldown is a real, deliberate ADDITION.** The prototype's `authResend` (**2145**) is pure simulation: it flips `S.otpResent=true`, flashes `Code sent again ✓` for 2000ms, and never rate-limits anything. GoTrue does rate-limit, and a resend inside the window returns an error rather than a code. **Measured in this repo's own `supabase/config.toml`, not assumed:** `[auth.email] max_frequency = "1s"` and `[auth.sms] max_frequency = "5s"` locally — **not the 60s the consultation asserted**; the 60s figure is the hosted-platform default, which is what production will actually run. So the UI must handle a genuine cooldown regardless of how permissive local dev is. The addition is minimal and mechanical: the resend control disables itself for the cooldown window and says so, then returns to the prototype's exact `Didn't get it? Send again` / `Code sent again ✓` pair. New copy is authored, registered in `screenCopy.ts`, swept by the content-safety guardrail, and listed in Open Question 2 for sign-off. **This is a small deliberate addition to locked copy, not a deviation from it** — the prototype has no cooldown state at all to deviate from.
- **D3 — `'superseded'` is a new `CaseOutcome` member, with authored copy.** The migration's genuine conflict case (both the account and this device hold a `still_open` case for the same service) is resolved in favour of the **account's** case; the local one is uploaded rather than discarded, and it needs an outcome that is neither `still_open` (the server's partial unique index forbids a second one, correctly) nor a lie. `'closed_unresolved'` would assert *"every verified step used"*, which did not happen. So: `'superseded'`, named to match the file's existing terminal-state naming (`'deliverable_received'`, `'closed_unresolved'` — past-participle, snake_case, describing what happened to the case rather than what the citizen did). It carries **three** authored strings — one `LOG_COPY` entry, one card kicker and one casefile headline — all registered, all signed off in Open Question 2. (The headline was added during that sign-off consultation; the original draft had two.) **This deviation has a much larger blast radius than it looks — see Task 5**; three render sites and one reducer path branch on `outcome` today and every one of them treats "not `still_open`" as "closed", which would render a superseded case as *"Closed — unresolved"* and offer to reopen it.
- **D4 — case ids become `crypto.randomUUID()`, injected on the action payload.** `completeSave` mints `'c' + payload.now` (`session/cases.ts:266`). Two devices saving in the same millisecond mint the same id, and under C7 those two ids collide inside a single account on a primary key of `(user_id, id)` — one citizen's case silently overwrites their other one. This is a real (if unlikely) data-loss bug that only becomes reachable when an account can span devices, which is exactly what this chunk builds. The fix follows **C5's own deviation D6** rather than inventing a new pattern: the reducer stays pure, so the id is *injected* on the action payload (`{ type: 'BEGIN_SAVE', …, newId: string }`), minted at the dispatch site by a single `newCaseId()` helper in `session/cases.ts`. Unlike `now`, this one has no lint friction — it is called inside an `onClick`, never during render, so oxlint's `react/purity` rule never sees it. Existing tests asserting the old format are two lines (`cases.test.ts:326` and `:328`) and are updated, not deleted.
- **D5 — reopening a closed case is gated on the one-active-case-per-service invariant.** `reopenCase` (`session/cases.ts:792-802`) sets `outcome: 'still_open'` unconditionally. Today that can already produce two `still_open` cases for one service (close a passport case, start and save another, reopen the first) — a latent invariant violation that `localStorage` happily accepts. Under C7 the server's `casefiles_one_open_per_service` partial unique index rejects it, and because the migration and the ordinary save path both write through the same upsert, **the rejection takes down the whole write, not just the reopen.** The fix is a **gate, not an invention** (same principle as C5's OQ1(b) ruling on `CaseClosedScreen`): the reopen control does not render when a `still_open` case for that `engineKey` already exists, and `reopenCase` itself returns `null` in that state. No replacement copy is authored — the control is simply absent, exactly as `SaveControl` is absent once a case is saved.
- **D6 — sign-out clears the session and never writes server cases into `localStorage`.** The prototype's `signOut` (**2155-2159**) sets `S.user=null; S.savedCases=[]` and deletes `nm_user`, deliberately leaving `nm_cases` in storage — *"cases stay on the account and come back at the next sign-in"* — because in a simulation, storage **is** the account. In the real build the account's cases were never in storage, so nothing is left behind and nothing is written back. Same visible behaviour (sign out → Home shows no cases; sign back in → they return), different mechanism, and it closes a genuine cross-account leak: without this, signing out of account A and into account B on the same browser would migrate A's cases onto B. Task 8 carries the test, and it asserts the *absence* of a write.
- **D7 — `maskId` reads the sign-in identifier, not `user.id`.** The prototype's `S.user` is `{ method, id }` where `id` is the phone number or email address, and `maskId` (**2146-2151**) slices it. Supabase's `user.id` is a UUID and `user.phone`/`user.email` carry the identifier. A faithful-looking transcription that passes `user.id` into `maskId` produces `+91 •••••• 4f2` from a UUID — visually plausible, completely wrong, and it would ship. The port introduces one adapter (`toAppUser(supabaseUser)` in `session/auth.ts`) that maps a Supabase user to the prototype's own `{ method, id, name }` shape at exactly one place, and `maskId` is otherwise transcribed verbatim. Task 3 carries a test with a real UUID in `user.id` and a real phone in `user.phone`, asserting the mask reflects the phone.
- **D8 — the Google-name backfill shim (1962-1969) is NOT ported.** It exists only because the prototype's simulation had no profile to read from for sessions created before the name feature: `if(S.user && S.user.method==='google' && !S.user.name){ S.user.name='Ananya'; }`. Its own comment says why — *"a Google session always carries a profile name in production (OAuth supplies it every load), so the sim mirrors that here."* Real OAuth supplies `user_metadata.full_name` on every load, so the real read-order (D9) makes the shim dead by construction. Not ported, and no hardcoded name appears anywhere in the shipped code.
- **D9 — the displayed name has a three-step read order, and no `profiles` table.** `user_metadata.display_name` (set by the citizen on `SaveNameScreen`) → `user_metadata.full_name` (supplied by Google, always) → absent, in which case the masked id shows instead. This exactly reproduces the locked behaviour *"Google always has a name; phone/email never does until added"* without a second table, a trigger, or a `SECURITY DEFINER` function. Written with `supabase.auth.updateUser({ data: { display_name } })`.
- **D10 — `adoptStoredCases()` becomes an async server fetch.** Prototype **2118**: `S.savedCases = store.get('nm_cases') || []`. In the real build it is `fetchRemoteCases()` — an awaited `select` — and the sign-in flow therefore has a loading state the prototype does not (the prototype's `S.restoring` field, **1948**, is declared but never assigned anywhere in the lock; it is not ported, and the loading state is derived from the real async status instead).
- **D11 — where the account-chip spec and the prototype disagree, the prototype wins.** One instance, in the sign-out confirm: the spec writes *"Sign out? Your cases stay on your account — sign back in any time."* (em-dash); the prototype ships *"Sign out? Your cases stay on your account. Sign back in any time."* (**2257**, period, two sentences). Transcribe the prototype's. Recorded because the two are close enough that a reader checking the spec would "correct" the shipped string.
- **D12 — `state.authId` holds E.164 with the `+`; GoTrue's `user.phone` holds it without. Both are correct, and the two must never be assumed equal.** The prototype's `authSubmitId` (**2106-2109**) stores bare ten digits (`'9876543210'`) and every downstream reader re-adds `+91` by hand — `renderSaveOtp`'s destination is `'+91 ' + S.authId` (**3847**) and `maskId` hardcodes `'+91 •••••• '` (**2148**). The real build cannot store bare digits: `signInWithOtp` requires E.164, so `normalisePhone` returns `'+91' + digits` and *that* is what `AUTH_ID_SUBMITTED` writes into `state.authId`. **Verified empirically against the running local stack, not assumed:** creating a user with `phone: "+919876543210"` returns `phone: "919876543210"` — GoTrue **strips the leading `+`** on storage, matching the `[auth.sms.test_otp]` key convention Task 1 already records. So the two identifiers coexist in different shapes and each consumer must be written against the one it actually reads:
  - `state.authId` → `'+919876543210'`. The OTP screen's destination is therefore **`'+91 ' + authId.slice(3)`**, reproducing the prototype's exact `+91 9876543210` display from the new stored shape (Task 12).

## Task 2 — The `casefiles` table, the one-open-per-service index, and RLS

**Files:** `supabase/migrations/<timestamp>_casefiles.sql` (new), `supabase/migrations.test.ts` (new)

**Design notes**

1. **The schema mirrors `src/domain/casefile.ts`; it does not reinvent it.** Read that file first. Three columns are promoted out of the object because the *server* needs them to enforce something (`user_id` for RLS, `engine_key` and `outcome` for the partial unique index); everything else stays inside one opaque `data` JSONB blob. Postgres learns nothing about diagnoses, and C8 adding fields to `Casefile` needs no migration.
2. **The migration, verbatim** (create it with `npx supabase migration new casefiles` so the timestamp prefix follows CLI convention):
   ```sql
   create table public.casefiles (
     user_id     uuid not null default auth.uid() references auth.users(id) on delete cascade,
     id          text not null,
     engine_key  text not null check (engine_key in ('passport','voter','sir')),
     outcome     text not null check (outcome in ('still_open','deliverable_received','closed_unresolved','superseded')),
     data        jsonb not null check (pg_column_size(data) < 65536),
     updated_at  timestamptz not null default now(),
     primary key (user_id, id)
   );

   create unique index casefiles_one_open_per_service
     on public.casefiles (user_id, engine_key) where outcome = 'still_open';

   alter table public.casefiles enable row level security;

   create policy "own rows: select" on public.casefiles for select to authenticated
     using ((select auth.uid()) = user_id);
   create policy "own rows: insert" on public.casefiles for insert to authenticated
     with check ((select auth.uid()) = user_id);
   create policy "own rows: update" on public.casefiles for update to authenticated
     using ((select auth.uid()) = user_id) with check ((select auth.uid()) = user_id);
   create policy "own rows: delete" on public.casefiles for delete to authenticated
     using ((select auth.uid()) = user_id);

   revoke all on public.casefiles from anon;
   grant select, insert, update, delete on public.casefiles to authenticated;
   ```
   **On the two privilege statements, because both are easy to get wrong in opposite directions.**
   - The **`grant` is explicit on purpose.** Supabase's base image sets default privileges that already grant `anon`/`authenticated`/`service_role` on new `public` tables, so omitting it works — *on Supabase*. Relying on it means a `db reset` replaying these migrations against a plain Postgres produces a table `authenticated` cannot write, and the failure surfaces as an opaque permission error far from its cause. One line removes the ambiguity. It is written **after** the `revoke ... from anon` so the two cannot be read as interacting; they address different roles and do not.
   - **There is no column-level `revoke update (user_id)`, deliberately.** An earlier draft carried one as "belt to the `with check` policy's braces". It is not a belt — it is a **no-op**: in Postgres a column-level `REVOKE UPDATE` has no effect while the role still holds table-level `UPDATE`, which `authenticated` does and must. Worse, a version that *did* bite (revoking table-level UPDATE and re-granting per column) would break the app outright, because `upsert` sends `user_id` in the row payload and an on-conflict UPDATE would then be denied. **The `with check ((select auth.uid()) = user_id)` clause on the UPDATE policy is the sole and sufficient protection against user_id reassignment**, and the SQL comment must say exactly that rather than crediting a statement that does nothing. There is no live vulnerability here either way — only a false account of why.
3. **Five things in that SQL are load-bearing and each has its own test, because each fails silently if removed.**
   - **`(select auth.uid())`, never bare `auth.uid()`.** The subselect form is evaluated once per query; the bare form is evaluated per row. On a table this small the difference is invisible — which is exactly why it would get "simplified" later.
   - **`with check` on the UPDATE policy, not just `using`.** Without it, a signed-in user can update one of their own rows and **reassign its `user_id` to someone else's account** — `using` gates which rows they may touch, `with check` gates what the row may become. This is a real, specific privilege footgun, not a stylistic preference, and per design note 2 this clause is the **only** thing standing in that gap. Its live test (the `rls.live.test.ts` bullet below) is therefore the single most important assertion in the chunk's SQL, and it is a test a column-level revoke would have made *unfalsifiable* — it passes either way, which is exactly why the no-op looked like protection.
   - **The partial unique index is the actual guarantee of one-active-case-per-service.** `session/cases.ts`'s `completeSave` enforces it client-side for instant UX; the client is never trusted, so the constraint exists server-side too. **Both must exist.** Deleting either is a defect: without the client check the citizen gets a server error instead of a merge; without the index the invariant is a suggestion.
   - **`revoke all … from anon` plus `to authenticated` on every policy.** This is the mechanism that makes *"the diagnosis you just got never required signing in"* structurally true rather than a promise: an anonymous browser cannot read or write a single row, whatever the client code does.
   - **The `outcome` check constraint includes `'superseded'`** (D3, Task 5). It is written into the migration now, ahead of the TypeScript union, because a migration is the one thing in this chunk that is painful to amend later.
4. **No `SECURITY DEFINER` function is needed and none is added.** The whole migration path runs as ordinary authenticated-client upserts under these policies. The guardrail test below exists to keep that true.
5. **The three `supabase/*.test.ts` files sit outside `tsconfig.app.json`'s `"include": ["src"]`, and that has one consequence worth knowing before writing them.** vitest runs them (its own resolution is independent of the tsconfig `include`), but **`tsc -b` never type-checks them** — so a type error in `config-auth.test.ts`, `migrations.test.ts` or `rls.live.test.ts` will not fail `npm run build`, and `migrations.test.ts` in particular *imports typed source* (`CASE_OUTCOMES` and `ServiceKey`/`SERVICE_KEYS` from `src/domain/casefile.ts`) from an unchecked file. The practical rule: those imports are verified by the test **failing at runtime**, not by the compiler, so assert on the imported array's contents rather than leaning on its type. Do **not** widen `include` to fix this — `src` is deliberately what ships, and pulling `supabase/` into the app project would put `node:fs` into the app's type graph.
6. **Two layers of test, and the second one matters more.** A static test that greps the `.sql` catches deletion and typos; it cannot catch "the policy is present but does not do what it says". So Task 2 also ships a **live-stack integration test**, skipped by default (`describe.skipIf(!process.env.NEXTMOVE_SUPABASE_LIVE)`) so CI and the ordinary `npm test` run stay hermetic, and **run by hand at least once in this task, with its output recorded in the completion note.** A skipped test that has never been run is not evidence.

## Task 7 — `caseSync.ts`: remote read/write and the sign-in migration

**Files:** `src/session/caseSync.ts` (new), `src/session/caseSync.test.ts` (new)

**This is the riskiest module in the chunk and it is built with no UI attached, deliberately.** Get the shape right against a fake client, prove every branch including failure, and only then wire anything to it. An independent assessment of this chunk named this function specifically as the piece most likely to lose a citizen's data.

**Design notes**

1. **Row shape ↔ `Casefile`, one adapter pair, both directions tested.**
   ```ts
   caseToRow(userId, c) → { user_id: userId, id: c.id, engine_key: c.engineKey, outcome: c.outcome, data: c, updated_at: <iso> }
   rowToCase(row)      → row.data as Casefile
   ```
   `data` stores the whole `Casefile` **including** the fields promoted into columns. The duplication is deliberate: the columns exist for the server's constraints, `data` is the client's record, and a round trip must be lossless without the client reassembling an object from columns. Test the round trip on a maximal fixture — one with `closedAt`, a non-empty `log`, a non-null `remindAt`, a sparse `prepChecks` and a non-null `sirPhaseId` — and assert `toEqual`, not a field-by-field spot check.
   **`unsaved?: true` must never reach the server**: a working case is by definition not saved, and a row carrying `unsaved` would come back and make a saved case render as unsaved. Strip it in `caseToRow` and assert it.
2. **`fetchRemoteCases()`** — `select('*')` (RLS scopes it to the caller, so no `.eq('user_id', …)` is needed or wanted; adding one implies the filter is what protects the data, which it is not) → `rowToCase` each → sorted **newest first by `savedAt`**, matching the order `completeSave` maintains locally with its `unshift` and that Home renders directly. Returns `{ ok: true, cases } | { ok: false, error }`. **Returns `{ ok: false }` with no call attempted when there is no session** — the Global Constraint, tested.
3. **`pushCases(cases)`** — a single `upsert(rows, { onConflict: 'user_id,id' })`. One call, not N. Same no-session guard.
   **Where `caseToRow`'s `userId` comes from, since `pushCases` takes only cases.** It comes from the very same read that implements the no-session guard: `pushCases` calls `getClient().auth.getSession()` once, returns `{ ok: false }` when there is no session, and otherwise uses that session's `user.id` as the `userId` for every `caseToRow` call. **One read, one source** — the guard and the id can never disagree, and no caller has to thread a user id it might get wrong. `fetchRemoteCases` reads the session for the guard alone; it needs no id, because RLS does the scoping (design note 2).
4. **`migrateLocalCases(local, remote, now)` is a PURE function, and this is the design decision that makes the whole thing testable.** It takes the two lists plus an injected clock (D6 — `now` is the timestamp on the appended journal entry, design note 9) and returns a **plan**:
   ```ts
   { toUpload: Casefile[]; adopted: Casefile[]; merged: Casefile[] }
   ```
   It performs no I/O, calls no clock, mints no id, and touches no storage. **That signature is the one signature** — an earlier draft cited a two-argument form elsewhere in this task; there is only the three-argument one. The impure orchestration — fetch, plan, push, then clear local — lives in a separate thin `runSignInMigration()` whose only logic is ordering and failure handling. Testing four conflict states plus a whole-batch failure against a pure function and a four-line orchestrator is tractable; testing them against one async function that does everything is not.
   **`merged` exists because `adopted` alone is the wrong thing to render, and nothing else in the system would catch that.** `adopted` is what the *server already held*; `toUpload` is what this device just contributed. What the citizen must see after signing in is **both** — so `merged` is `adopted` concatenated with `toUpload`, sorted **newest-first by `savedAt`** to match `fetchRemoteCases`'s order (design note 2) and Home's render order. It is computed inside the pure function, not assembled at the call site, specifically so the union cannot be got wrong by a caller: `ADOPT_CASES` takes `merged` verbatim.
   **The consequence of getting this wrong is the exact failure C7 exists to prevent.** A citizen with device-local casefiles signing in for the first time has `remote === []`, so `adopted === []` and `toUpload` is their whole life's worth of cases. Dispatching `adopted` there clears `nm_cases` (the push succeeded, so the clear is correct), replaces `savedCases` with `[]`, and renders an empty Home. The data is safe on the server and completely invisible until a reload. Assert `merged` in every one of the four state tests below, not just in the conflict one.
5. **Rule zero, applied before the conflict table: a local case whose `id` already exists in `remote` is the SAME case, not a conflict.** Ids are stable (a UUID under D4, or the stable `'c' + savedAt` for a legacy case), so an id match means this exact case is already on the server. Such a case is dropped from `toUpload` and its **remote** copy goes into `adopted` — the remote copy wins, because it is at least as fresh and may carry an edit made on another device that re-uploading would overwrite.
   **This rule is not hypothetical; it is what makes design note 7's idempotence claim actually true.** A crash between the push and the local clear leaves the citizen with the same cases in both places. Without rule zero the retry sees "account has a `still_open` passport case, local has a `still_open` passport case", declares a conflict, and marks the citizen's own case `superseded` **against itself** — a self-inflicted data change that looks exactly like a correct conflict resolution in the logs. Rule zero is checked first, unconditionally, and it carries its own test.
6. **The migration rule, per service (`engineKey` ∈ `passport` | `voter` | `sir`), applied to whatever survives rule zero. Confirmed by the repo owner and not to be re-litigated — but recorded here as a made decision, with its reasoning:**
   | account has `still_open`? | local has `still_open`? | what happens | where it lands |
   | --- | --- | --- | --- |
   | yes | no | nothing to do — the account's case is simply adopted | `adopted` |
   | no | yes | the local case uploads as-is, `user_id = auth.uid()`, unchanged | `toUpload` |
   | no | no | nothing to do | — |
   | **yes** | **yes** | **the ACCOUNT's case stays `still_open`.** The local case still uploads, with `outcome: 'superseded'` (D3) and **one** appended journey-log entry, `LOG_COPY.superseded` | account's → `adopted`; local's → `toUpload` |

   **The fourth column is why the conflict row is not the interesting one.** In every row the local case ends up in `toUpload`, and `toUpload` is half of `merged` (design note 4) — so the case a citizen can actually see after signing in is the union of both columns, never `adopted` alone. `adopted` and `toUpload` are disjoint by construction (rule zero removes the only way they could overlap), so `merged` needs no deduplication, and a test asserts that disjointness directly rather than assuming it.
   **Why the account wins:** the account's case is the one that has survived across devices and sessions and is the one the citizen will find on every other device; the local one exists on exactly this browser. Losing the local one entirely would be data loss, so it is kept in full — its whole journey log intact — as a record rather than as a live case. The conflict can occur **at most once per service** because both sides already enforce one-active-per-service, which is what makes this table exhaustive rather than a heuristic.
7. **Everything that is not `still_open` uploads unconditionally** (after rule zero). Closed, deliverable-received and already-superseded local cases can never collide with the partial unique index, so they need no conflict logic at all — they are simply included in `toUpload`, and therefore in `merged`. State this explicitly; it is the reason the table above only ever discusses open cases.
8. **Idempotence is a requirement, not a nice-to-have.** The upsert is keyed on `(user_id, id)`, so a crash after the push but before the local clear, followed by a retry, produces the identical end state rather than duplicates — **and, via rule zero, without re-resolving the retry as a conflict.** Test it directly: run the whole orchestration twice against the same fake, assert the second run's upsert payload equals the first's, that no row is duplicated, and that **no case acquired a `superseded` outcome on the second run**.
9. **The clear-order rule, which is the single most important line in this file.** `runSignInMigration` clears `nm_cases` **only after** `pushCases` has resolved `{ ok: true }`. Never before. Never on `{ ok: false }`. There is no "optimistic" variant of this and no reordering of it for readability. A network failure at the wrong moment with the wrong order silently destroys a citizen's case, and they will never know it existed.
   **The push is one `upsert` call, so its failure is whole-batch, never partial** — there is no half-written server state to reason about, and the earlier draft's "mid-batch failure" was a misnomer for a single-call rejection. Say *whole-batch* or *push-failure*; the accurate name is what tells a reader they do not need reconciliation logic.
   **And the guarantee does not end when this function returns.** Preserving `nm_cases` here is only half of it; the citizen may sign out afterwards, and `SIGN_OUT` must not then write `[]` over the rows this path protected. That half lives in Task 4's `SIGN_OUT { localCases }` payload and Task 8's effect gating, and is tested end-to-end in Task 8. Neither half is sufficient alone.
10. **`log` append semantics.** The superseded entry is appended with the existing `appendLog` helper's shape (`{ t, kind, text }`), `kind: 'closed'` — the nearest existing `JourneyEntryKind`, since C7 adds no new kind (a new kind would ripple into `JourneyLog`'s rendering and `checkinPatches`' typing for one entry). `t` is the injected `now` from `migrateLocalCases(local, remote, now)`, never `Date.now()`, following D6.

## Task 8 — `caseStore.ts` becomes account-aware; App.tsx's auth lifecycle

**Files:** `src/session/caseStore.ts` + test (modify), `src/App.tsx` + test (modify)

This is where C5's deviation **D2** seam is finally filled — `caseStore.ts`'s own comment already names it: *"C7: account-scoping goes here."*

**Design notes**

1. **`caseStore.ts` stays the only file that touches `localStorage`** and stays synchronous. It gains exactly one function, `clearLocalCases()` (`store.del(NM_CASES_KEY)`), and its doc comment is rewritten from *"no server-side account exists yet"* to what is now true. `loadCases()`/`saveCases()` are **unchanged in behaviour** — the account gate lives in App.tsx, where the auth state actually is, not inside a storage module that would have to import auth to ask.
2. **The prototype's account gate, and what it means here.** Prototype **1974**: `S.savedCases = S.user ? (store.get('nm_cases') || []) : []` — *"signed out, stored cases stay in storage but never render."* In the real build the two halves separate: **signed out**, `savedCases` comes from `localStorage` and renders (tracking never requires an account — Product Principle #4, and C5 shipped exactly this); **signed in**, it comes from the server and `localStorage` is empty because the migration cleared it. The prototype's gate is an artefact of storage doubling as the account. The *observable* rules C7 must preserve are the two the locked design actually states: after sign-out Home shows no cases, and signing back in brings the account's cases back.
3. **The boot sequence in `App.tsx`, in order:**
   1. `useReducer`'s lazy initializer seeds `savedCases: loadCases()` — **unchanged from C5**, synchronous, never throws, so the first paint is instant and never blocks on the network.
   2. A mount effect calls `getCurrentUser()`. If there is a live session: `dispatch(SIGNED_IN)`, then the migration (design note 4's single entry point).
   3. A subscription to `onAuthChange` handles everything after that.
4. **The migration has ONE entry point and it is guarded in the reducer, because it has TWO independent triggers.** This is where an earlier draft was thin, and the thinness is the hazard: the mount effect's `getCurrentUser()` (3.2) and the `onAuthChange` subscription (3.3) are separate code paths, and on a real PKCE return **both fire** — the mount effect finds the session supabase-js just exchanged, while GoTrue emits `INITIAL_SESSION` and then `SIGNED_IN` on the same channel. That is up to three triggers for one sign-in, not the two an event-filter alone would address.
   So: a single local `async function startMigration()` is the only thing that ever calls `runSignInMigration`, and its first line is `dispatch({ type: 'MIGRATION_STARTED' })`. The guard is **Task 4's reducer arm**, which no-ops when `migration` is already `'running'` or `'done'` — and `startMigration` reads the status back before proceeding, so a losing trigger returns without touching the network. **A reducer guard, not a `useRef`:** a ref lives in one effect and the second call site is precisely the one that will not have it; reducer state is shared, inspectable and assertable.
   On resolution: `{ ok: true, cases }` → `dispatch({ type: 'ADOPT_CASES', cases })` (which also sets `'done'`); `{ ok: false, error }` → `dispatch({ type: 'MIGRATION_FAILED', error })`.
   **The concrete harm the guard prevents, stated so it is not optimised away:** the upsert's idempotence (Task 7 design note 8) means the *server's* end state survives a double run, but the second run reads `nm_cases` **after** the first cleared it, sees an empty local set, and produces a plan whose `merged` omits everything this device contributed — which then replaces `savedCases`. The citizen's cases are on the server and gone from the screen.
   `INITIAL_SESSION` is still filtered out of the event handler as well (belt to the reducer's braces, and it costs one line), but the plan does **not** rest on that filter alone.
5. **The other `onAuthChange` events, named rather than left undefined.** They all arrive on the same channel and an unhandled event is a decision made by accident. Exhaustively:
   - **`SIGNED_IN`** — `dispatch(SIGNED_IN)`, then `startMigration()`. The main path.
   - **`INITIAL_SESSION`** — **ignored.** The mount effect (3.2) already covers the boot-with-a-session case, and this event's session is the same one. Ignoring it removes one of the three triggers at the source.
   - **`SIGNED_OUT`** — `dispatch({ type: 'SIGN_OUT', localCases: loadCases() })`, and **nothing else** (no `auth.signOut()` call — the sign-out already happened, here or in another tab). This is what makes a sign-out in a second tab coherent in this one. It also fires for *our own* sign-out, so the dispatch runs twice; `SIGN_OUT` on an already-signed-out state resets to the same value, so it is idempotent by construction. Test that it is.
   - **`USER_UPDATED`** — `dispatch({ type: 'SET_USER_NAME', name: toAppUser(session.user)?.name ?? null })`. Fired by `setDisplayName`'s `updateUser` call (Task 13), so the chip's name is refreshed from the authoritative server echo. Task 13 also updates it optimistically; both land on the same arm with the same value, so the second is a no-op. **Not `SIGNED_IN`** — see Task 4's action list for why that would wipe three unrelated fields.
   - **`TOKEN_REFRESHED`** — **explicitly ignored.** The access token rotated; the user identity did not. Re-dispatching `SIGNED_IN` would clear `authErr`/`otp`/`authBusy` mid-flow, and re-running the migration would be worse. Write the `case` with the reason in a comment rather than letting it fall through an unremarked `default`.
   - **`PASSWORD_RECOVERY` / `MFA_CHALLENGE_VERIFIED`** — **unreachable and ignored**, because scope exclusion 4 ships no password auth and no MFA. Named so a reader does not have to re-derive that they are impossible.
6. **Strip `?code=` UNCONDITIONALLY, not only on success.** supabase-js consumes the code itself; leaving it in the address bar means every subsequent refresh retries an already-used code. Doing the strip only "after the session is confirmed" gets the failure case exactly backwards: **a failed exchange is precisely the case that leaves a dead `?code=` in the URL to fail again on every reload**, and the citizen has no way to clear it but to edit the address bar. So the strip runs in the mount effect once the exchange has *settled*, whichever way it settled: `history.replaceState(null, '', window.location.pathname)`. Note the wider fact this depends on: **no other file in `src/` reads `window.location`** (verified), so this is the app's only interaction with the URL and nothing else can be disturbed by rewriting it.
7. **The persistence effect splits in two, and the split carries both the D6 leak fix and the migration-race fix.**
   - Signed **out**: the existing `useEffect(() => saveCases(state.savedCases), [state.savedCases])`, unchanged, but **gated on `state.user === null`**.
     **Without that gate, the account's cases get written into `localStorage`, and the next different account to sign in on the same browser migrates them onto itself.** That is a real cross-account data leak with a one-line cause, and it is the reason D6 exists. Test it by asserting the *absence* of a write.
     This effect needs **no further exception for the failed-migration case**, because Task 4's `SIGN_OUT { localCases }` payload guarantees that post-sign-out `savedCases` always equals what `nm_cases` actually holds (see design note 9). The gate is `user === null` and nothing more.
   - Signed **in**: a second effect pushes to the server on change, and **must not** call `saveCases`. Its dependency array is **`[state.savedCases, state.user, state.migration]`** and its gate is **`state.user !== null && state.migration === 'done'`** — both were unspecified in an earlier draft, and both are load-bearing:
     - during `'running'` it would race the migration's own `upsert` with a `savedCases` that is still the *local* set (`SIGNED_IN` lands before `ADOPT_CASES`), pushing rows the conflict resolution had not yet seen;
     - immediately after `ADOPT_CASES` it fires once with the just-adopted set and pushes it straight back — harmless in content (the rows are byte-identical and the upsert is keyed on `(user_id, id)`) but a wasted round trip, so the implementation additionally skips a push when `savedCases` is reference-identical to what `ADOPT_CASES` delivered;
     - during `'failed'` it would push to a server that just rejected the write, and the error would surface a second time from a path the citizen did not trigger.
8. **Failure states are visible, not swallowed.** A failed fetch or push dispatches `MIGRATION_FAILED`, which sets `authErr`, and the citizen sees it. Silently failing to save a case they were told is saved is worse than an error. There is **no automatic retry** (scope exclusion 7); the next sign-in re-runs the migration against the still-intact local set, which is the recovery path.
9. **Sign-out never writes a server case into `localStorage`, and never destroys a preserved local one.** These are two different guarantees and an earlier draft only had the first.
   - The first is D6's: no case fetched from the account may reach `nm_cases` on the way out. That holds because the signed-in half of the split effect never calls `saveCases` at all.
   - The second is the Global Constraint's second half, and it is the one with a real bug behind it. If the migration **failed**, `nm_cases` still holds the citizen's cases — deliberately, by Task 7's clear-order rule. The citizen is nonetheless signed in (`state.user` is set), so the moment they sign out, a `SIGN_OUT` that hardcoded `savedCases: []` would empty state, the signed-out effect would fire with `[]`, and `saveCases([])` would overwrite **the very rows the failure path protected.** A failure that correctly preserved the data, followed by an ordinary sign-out, destroys it.
     The fix is structural rather than a special case: **`SIGN_OUT` carries the local set on its payload** (Task 4), read at the dispatch site with `loadCases()`. Post-sign-out `savedCases` is then *by definition* whatever `nm_cases` holds — `[]` after a successful migration (identical to the locked behaviour, D6 intact) and the preserved cases after a failed one, which also means they stay visible on Home instead of vanishing until the next reload. The signed-out effect writing that value back is then either `[]` over an empty key or the same rows over themselves. **Neither can lose anything, so no suppression flag, no effect-ordering trick and no migration-status exception is needed on the write path.** There are exactly two dispatch sites for `SIGN_OUT` (the popover's confirm in Task 15, and the `SIGNED_OUT` event handler in design note 5) and both must pass the payload; a required, non-optional payload field is what makes forgetting it a compile error rather than a data-loss bug.

**1. The `Topbar` account-slot shape (Task 15 design note 2) — RESOLVED: OVERTURNED in favour of a required `state: SessionState` prop.** The plan's original call was a required `account: ReactNode` slot filled identically at every site.    It was adopted because it keeps the whole benefit the original call was made for — the compiler enumerating every mount site until each is wired — while answering two things the `ReactNode` version could not: the slot's value is textually identical at all 25 sites (ceremony, not a per-site decision), and at the 8 test mounts `account={null}` would be a legitimate, compiling, chip-free answer that silently retires the compile-time check, whereas `state={initialSession}` is both correct and genuinely renders nothing. The rejected-restructure objection was checked against the real file and does not apply: `Topbar.tsx` already imports from `../session/session` (**14**), so this adds a type import to an existing dependency and removes nothing.
